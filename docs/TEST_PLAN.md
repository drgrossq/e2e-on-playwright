# Тест-план SauceDemo

## Цель и объект

Проверить ключевой путь покупателя и наиболее значимые состояния интерфейса
[демо-магазина SauceDemo](https://www.saucedemo.com).
Объект — публичный веб-интерфейс, окружение — desktop Chromium.
Учётные записи предоставлены самим стендом; данные покупателя вымышленные.

В проекте нет отдельной утверждённой спецификации продукта. Ожидаемые сообщения,
каталог и ставка налога зафиксированы как тестовый базис демо-приложения.
При изменении стенда сначала следует уточнить ожидаемое поведение, затем менять тесты.

## Приоритеты и покрытие

| Риск                                             | Приоритет | Автоматизированные проверки |
| ------------------------------------------------ | --------- | --------------------------- |
| Покупатель не может завершить заказ              | Высокий   | SMK-01, CHK-02              |
| Неверная стоимость или состав заказа             | Высокий   | INV-01, CHK-02              |
| Вход с неверными данными или доступ после выхода | Высокий   | AUTH-01–03, MNU-03          |
| Потеря или неверное удаление товаров             | Высокий   | CR-01–02, MNU-02            |
| Пропуск обязательного поля покупателя            | Средний   | CHK-01                      |
| Ошибочный порядок или детали товара              | Средний   | INV-02–04                   |
| Невозможность закрыть навигацию                  | Средний   | MNU-01                      |

Приоритет — порядок проверки в рамках этого проекта, а не оценка ущерба реальному бизнесу.
Все 15 сценариев и теги перечислены в [README](../README.md#описание-тестовых-сценариев).

## Применённые техники

- Классы эквивалентности для входа: валидный пользователь, заблокированный пользователь,
  неверный пароль, отсутствующий username, отсутствующий password.
- Переходы состояний корзины: 0 → 1 → 2 товара, затем 2 → 1 → 0; отдельно сброс
  и очистка после оформления заказа.
- Проверка сохранения состояния: перезагрузка страницы корзины и возврат в каталог.
- Проверка порядка: переход с Z–A на A–Z и проверка всех значений, а не только первого.
- Независимый расчёт ожидаемой стоимости по тестовым данным; отдельные assertions для
  состава, количества, суммы товаров, налога и итога.

AUTH-03 проверяет порядок ошибок обязательных полей в одном сценарии.
CR-02 проверяет два последовательных состояния удаления. Это осознанная группировка
связанных действий в компактном наборе; при независимом развитии правил их стоит разделить.

## Предусловия и критерии завершения

Предусловия: установлен Node.js 22, зависимости из lockfile и Chromium; стенд доступен.
Setup должен успешно создать авторизованную сессию с пустой корзиной.
Каждый сценарий получает новый браузерный контекст; очистка общей сессии после теста не нужна.

Прогон принят, если статические проверки и все сценарии прошли без пропусков
и без успешного повторного запуска после падения. В CI это обеспечивает `failOnFlakyTests`.
При недоступности стенда результат фиксируется как инфраструктурная проблема,
а не автоматически как дефект магазина.

## Что проверить вручную или автоматизировать дальше

Пункты ниже — **план расширения**, их прохождение не заявляется.

| Область         | Следующие проверки                                                            | Почему не включены сейчас                                                |
| --------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Форма заказа    | Пустые Last Name / Postal Code, пробелы, длинные значения; отмена обоих шагов | Нужны отдельные правила валидации; сейчас показан один негативный пример |
| Корзина         | Добавление из карточки, возврат назад, прямой checkout пустой корзины         | Дополнительные ветви переходов                                           |
| Reset App State | Состояние кнопок Add/Remove сразу после сброса на открытом каталоге           | Текущий тест подтверждает очистку корзины, не всего UI                   |
| Сессия          | Back после logout, новый tab, перезапуск браузера                             | Текущий тест проверяет прямой вход в каталог                             |
| Каталог         | Price low–high, привязка каждой цены к названию после сортировки              | Приоритет отдан двум показательным сортировкам                           |
| Доступность     | Клавиатура, фокус, подписи полей, озвучивание ошибок                          | Отдельный вид проверки                                                   |
| Совместимость   | Firefox, WebKit, узкий экран                                                  | Основное окружение — Chromium                                            |

Проверки реальных платежей, доставки, API и БД, безопасности и нагрузки выходят за рамки
этого проекта. Публичный демо-стенд не используется для нагрузочных экспериментов.

## Разбор падения

1. Найти ID и первую упавшую проверку в HTML-отчёте.
2. Сопоставить ожидаемый результат с фактическим DOM, скриншотом и trace.
3. Воспроизвести один сценарий: `npm test -- --grep <ID> --trace on`.
4. Проверить, не изменились ли стенд, тестовые данные или предусловия.
5. Если подтверждён дефект продукта, оформить баг-репорт: заголовок, окружение,
   предусловия, шаги, ожидаемый и фактический результат, воспроизводимость, доказательства.
6. Если ошибка в тесте — исправить причину. Не заменять ожидание задержкой и не скрывать
   падение через `skip`, `force` или ослабление проверки.
